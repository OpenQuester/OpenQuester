# Dart vs Go server benchmark — 2026-07-18

## Result

For this combined Redis and PostgreSQL event workload, Go was substantially
faster than Dart on the measured server.

| Runtime | Application CPUs | Median events/s | Run range | Median p50 | Median p95 | Median p99 | Errors |
|---|---:|---:|---:|---:|---:|---:|---:|
| Dart | 1 | 2,087 | 1,925–2,110 | 28.83 ms | 41.35 ms | 50.02 ms | 0 |
| Dart | 3 | 2,564 | 2,543–2,616 | 23.67 ms | 39.17 ms | 50.55 ms | 0 |
| Go | 1 | 6,126 | 6,101–6,179 | 9.97 ms | 15.77 ms | 20.83 ms | 0 |
| Go | 3 | 4,880 | 4,517–6,269 | 12.06 ms | 22.62 ms | 29.56 ms | 0 |

The medians are calculated from three repetitions. At one application CPU, Go
delivered 2.94 times Dart's throughput and its p95 latency was about 62% lower.
At three application CPUs, Go's median throughput was 1.90 times Dart's and its
p95 latency was about 42% lower.

Dart gained about 23% from one isolate to three isolates. Go did not gain from
the additional application CPUs: its first three-CPU repetition reached 6,269
events/s, while the next two fell to 4,517 and 4,880. This is not evidence that
Go becomes intrinsically slower with more cores. Go already reached roughly
6.1k events/s on one application CPU, after which PostgreSQL, Redis, the load
generator, and the application competed on the same four-core host. The large
spread makes the Go three-CPU scaling result unsuitable as a pure runtime claim.

## Workload

Every successful `POST /event` request completed this ordered work before
returning HTTP `204`:

1. Decode the same JSON payload.
2. Increment a field in a run-specific Redis hash.
3. Insert one row into a normal PostgreSQL table with a composite primary key
   and timestamp.

Both services used HTTP keep-alive, the host network, 64 concurrent load
workers, and a total PostgreSQL pool limit of 24. Dart was AOT-compiled and used
one shared-port isolate per application CPU. Go used a native static binary and
set `GOMAXPROCS` to the application CPU count.

Each repetition had a five-second warm-up followed by 15 measured seconds. The
test order was Dart 1 CPU, Dart 3 CPUs, Go 1 CPU, then Go 3 CPUs. The service was
pinned to CPU 0 for the one-CPU case and CPUs 0–2 for the three-CPU case. The
load generator was pinned to CPU 3.

## Host and software

- CPU: Intel N100, 4 physical cores, no SMT.
- Memory: 10 GiB, no swap.
- Kernel: Linux 6.12.33-production+truenas, x86-64.
- Docker: 29.0.2.
- Dart: 3.12.2 stable, Linux x64.
- Go: 1.25.12, Linux amd64.
- PostgreSQL: 14.23.
- Redis: 7.2.14.
- Dart drivers: `postgres` 3.5.12 and `redis` 4.1.0.
- Go drivers: `pgx` 5.8.0 and `go-redis` 9.17.2.

The Dart and Go build images are pinned by digest in their Dockerfiles. The host
was left under its normal background workload; unrelated services were not
stopped.

## Validation

- 12 measured repetitions completed.
- 719,257 measured HTTP requests succeeded; none failed.
- For every repetition, the HTTP success count exactly matched both the
  PostgreSQL row count and the sum of Redis counters.
- After validation, 952,424 benchmark rows including warm-ups and all 24
  run-specific Redis keys were deleted. The reusable empty
  `runtime_benchmark.events` table remains.

## Limits and interpretation

This is a small full-stack driver/runtime benchmark, not a compiler benchmark.
It compares the language runtime, HTTP implementation, JSON implementation,
Redis driver, PostgreSQL driver, allocation behavior, and concurrency model as
one stack. Dart uses a multiplexed Redis connection per isolate, while Go's
Redis client uses its configured connection pool.

Absolute throughput should not be transferred directly to OpenQuester. Real
game actions add validation, locks, queue behavior, state mutation, Socket.IO,
logging, and broadcasts, and they do not necessarily insert a PostgreSQL row
for every event. The earlier estimated table therefore cannot be confirmed or
rejected by these absolute numbers.

The strongest supported conclusion is the stable one-CPU comparison: for this
small Redis-plus-PostgreSQL event path on this host, Go processed about three
times as many events per second as Dart at substantially lower latency. A clean
multicore language-scaling comparison would require a separate load-generator
machine and dedicated or CPU-isolated PostgreSQL and Redis instances, with the
configuration order randomized.
